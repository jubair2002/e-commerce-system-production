# Parity Testing Framework & Verification Protocol

This document explains the design, architecture, and operation of the automated parity testing suite located in `/parity-tests`.
Per project rules: **A route or module is considered "done" ONLY when it achieves a 100% clean parity report against the PHP implementation.**

## 2. Parity Test Components

### 1. Golden Test Vectors (`/parity-tests/golden/`)
Generated by executing the real, native PHP implementation without modifying any application code.
- **Fixtures Directory**: `parity-tests/golden/fixtures/`
- **Generated Fixtures**:
  - `money_formatting.json`: Precision decimal string outputs via `price()`.
  - `round.json`: Edge-case half-up rounding checks (`PHP_ROUND_HALF_UP`).
  - `cart_totals.json`: 200 varied cart combinations testing discounts, taxes, free shipping thresholds, and COD fees.
  - `shipping_districts.json`: All 64 Bangladesh districts mapped to zones (`inside_dhaka` vs `outside_dhaka`) and delivery rates.
  - `order_numbers.json`: Formatted order numbers (`ORD-YYYYMM-XXXX`).
  - `passwords.json`: Customer bcrypt hashes with SHA-256 pre-hashing and admin plain bcrypt hashes.
  - `hmac_tokens.json`: SHA-256 HMAC confirmation signatures using `APP_KEY`.
  - `crypto_aes.json`: OpenSSL AES-256-CBC ciphertexts and decrypted verifications.
  - `slugs.json`: Canonical slug generations.
  - `date_formatting.json`: Standardized ISO and human-readable date formats.
  - `json_float.json`: Floating point JSON serialization outputs.

### 2. Deterministic Fixture Database (`/parity-tests/seed/fixture_db.sql`)
Ensures identical initial states for both engines:
- Products: Simple active in-stock, simple on-sale with discounted pricing, out-of-stock items, and configurable/variable products with multi-attribute option matrix (Color, Size).
- Coupons: Active percentage (`SAVE10`), active fixed (`FLAT50`), high-threshold (`BIG500`), and expired coupons (`EXPIRED`).
- Customers: Verified active accounts, pending verification accounts, and temporarily locked accounts.
- Orders: Existing historical orders across all statuses (`pending`, `processing`, `shipped`, `delivered`, `cancelled`).
- Content: Storefront banners, categories, and published static pages.

### 3. Normalizer Engine (`/parity-tests/runner/normalizer.js`)
Prevents false-positive diffs caused by transient, dynamic, or non-functional tokens:
- **HTML DOM Normalization**:
  - Replaces dynamic CSRF tokens (`input[name="_csrf"]`, `input[name="csrf_token"]`, meta `csrf-token`) with a deterministic placeholder (`[CSRF_TOKEN]`).
  - Replaces checkout anti-replay tokens (`input[name="checkout_token"]`) with `[CHECKOUT_TOKEN]`.
  - Strips script nonces (`script[nonce]`).
  - Strips dynamic asset versioning query parameters (`?v=17...`).
  - Sorts element attributes alphabetically so attribute order differences do not trigger diffs.
  - Collapses insignificant inter-tag and intra-text whitespace.
- **JSON Normalization**: Recursively sorts JSON keys and strips dynamic token fields.
- **Text / CSV Normalization**: Canonicalizes line endings (`\r\n` -> `\n`) and trims trailing line whitespace.

### 4. Playwright Visual Diffing (`/parity-tests/runner/screenshot.js`)
Captures pixel-perfect screenshots across three responsive viewports:
- Mobile: `360 x 640`
- Tablet: `768 x 1024`
- Desktop: `1440 x 900`
- Injects CSS to disable all transitions and animations (`transition: none !important; animation: none !important;`) before snapping.
- Computes pixel-by-pixel diff with configurable threshold (default `0.0`).

### 5. POST Scenario Runner (`/parity-tests/runner/scenarios.js`)
Simulates critical user workflows (registration, login, cart manipulation, and checkout) and diffs resulting HTTP status, redirect targets, and database changes.

## 3. CLI Commands

Run parity commands from the repository root:

```bash
# 1. Run all parity test routes
make parity

# 2. Run a specific route by name
make parity ROUTE=shop
make parity ROUTE=product_simple
make parity ROUTE=cart_empty

# 3. Run all routes in a specific unit
make parity UNIT=storefront
make parity UNIT=api

# 4. Regenerate Golden Test Vectors
make golden

# 5. Run Rust Workspace tests and PHP test suites
make test
```

## 4. Reading Parity Results

When `make parity` finishes, it writes the interactive HTML dashboard to:
```
parity-tests/reports/index.html
```

### Interpreting Status:
- **PASS (Green)**: The Rust implementation emitted a response that is 100% structurally, semantically, and visually identical to PHP after token normalization. Status codes and redirect headers match exactly.
- **FAIL (Red)**: A discrepancy was detected. Click **"Toggle Diff"** in the HTML report to view the exact unified diff between PHP and Rust.

### Definition of "Done":
A ported page or endpoint cannot be marked as **Complete** in `docs/migration/PROGRESS.md` until:
1. It passes all unit and integration tests (`cargo test`).
2. It achieves a **PASS** with **0 diffs** in `make parity ROUTE=<name>`.
